Unit A3 - Anti-Tunnel-Vision Solution Judgment

FDE Dojo / Track A / Unit A3

Start with the reflex

A stakeholder describes a problem. Within seconds, an engineer's brain produces a familiar answer: "I'll write a script for that," or "this needs a new microservice," or "let's add a field to the database." That reflex fires before the problem is even fully understood - because it's the pattern the engineer already knows how to execute.

This is the narrow-focus failure mode in its purest form: reaching for the known tool before confirming it's the right-sized response. It feels productive (you're already coding) while actually skipping the one question that matters most.

The principle

Before committing effort, ask: "What is the smallest thing that would teach us something, or move the outcome, right now?" Not the smallest thing that's technically interesting. Not the smallest version of the solution you already had in mind. The smallest thing, full stop - which, per Unit A2, is very often "get the right person or agent involved for 15 minutes," not "write code."

This reframes "MVP thinking" away from "ship a smaller version of my planned feature" toward "find the cheapest possible way to learn whether my planned feature is even the right direction."

A simple test before building anything

Ask three questions, in order, before writing a line of code:

  1. What decision does this unblock? If you can't name one, you're building for its own sake.
  2. What's the cheapest way to get evidence for that decision? Often it's not code - it's a conversation, a query against existing data, a quick agent-drafted mockup.
  3. Only if the cheapest way still requires code - what's the smallest version of that code that produces evidence? Not the smallest version of the final feature - the smallest version that tells you if you're right.

Worked example

Stakeholder: "We should build a recommendation engine to suggest the right retirement plan to advisors."

Reflex answer: start designing a recommendation model.

Apply the three questions:

  1. Decision to unblock: whether advisors are currently picking suboptimal plans often enough to matter.
  2. Cheapest evidence: query existing data for how often advisors change their plan choice after a supervisor review - a proxy for "wrong first guess" - no model needed yet.
  3. If that data shows a real problem, then the smallest code is not a full recommendation engine - it's a simple rules-based suggestion for the single most common mistake pattern the data revealed.

The reflex ("build a recommendation engine") might still be right eventually - but arriving at it through evidence, in the right order, is the difference between an FDE and an engineer who happened to guess correctly.

The failure mode this corrects

This unit is the direct, practical antidote to "narrow focus / solution tunnel vision": it inserts a mandatory evidence-gathering step between "problem stated" and "code written," so the familiar tool only gets used once it's actually confirmed to be the right-sized response - not because it's the first thing that came to mind.

Self-check

Recall a time you started building something and only partway through realized it wasn't really what was needed. Apply the three questions retroactively - at which question would the mismatch have surfaced earlier?
