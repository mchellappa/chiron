Unit B2 - Requirements and Design

Start with a ticket an agent can't use

"Improve the renewals process." That's a fine thing to say to a human in a hallway. Handed to a Requirements-stage agent as a ticket, it produces nothing useful - the agent has no acceptance criteria to check against, no scope boundary to respect, and no way to know when it's done.

This isn't a new problem - it's Track A's Unit A1 (ambiguity has two causes) showing up again, except now the "listener" confused by the ambiguity is an agent instead of a person, and agents don't ask clarifying questions the way a human teammate might. The ambiguity has to be resolved before the ticket reaches the agent, not during.

The principle

"Agent-ready" means the ticket contains everything an agent needs to act without guessing: explicit acceptance criteria, explicit scope, and explicit non-goals. A human reading a vague ticket can go ask the author what they meant. An agent reading the same ticket either guesses (and is often wrong) or stalls.

What "agent-ready" actually looks like

Before a ticket enters stage:requirements-ready, it should answer:

  • Acceptance criteria - what observable condition means this is done? Not "renewals are faster," but "90% of renewals complete within 48 hours."
  • Scope - which part of the system/process does this touch? Named explicitly, not implied.
  • Non-goals - what this ticket deliberately does NOT attempt, so an agent (or the next human) doesn't quietly expand scope.
Not agent-ready
"Improve the renewals process."
Agent-ready
"Reduce renewal processing time at the underwriting handoff step from 5 days average to under 2 days. Scope: underwriting handoff only. Non-goal: do not change the advisor-facing renewal form."

From spec to sub-tasks: the Design stage

Once requirements are agent-ready, a Design-stage agent (or human) breaks the spec into sub-tasks with correct dependency links - e.g., a data-model change must finish before the integration that depends on it starts. This is where the ticket-state machine from Unit B1 starts to matter operationally: each sub-task gets its own label lifecycle, and the dependency order has to be reflected correctly (a Blocks-link, not just a list) so the choreography doesn't let a dependent sub-task start early.

Worked example

Spec: "Reduce renewal processing time at the underwriting handoff from 5 days to under 2 days." Design breaks this into:

  1. Sub-task: instrument the handoff step to measure current delay sources (no dependency, starts first)
  2. Sub-task: build the fix for the top delay source found (Blocks-link: depends on sub-task 1's findings)
  3. Sub-task: validate the 48-hour target against 3 weeks of post-fix data (Blocks-link: depends on sub-task 2 being deployed) - this is also the Unit A4 "outcome check," now formalized as its own tracked sub-task instead of an informal habit

Self-check

Take a real or plausible vague ask from your own work. Rewrite it as an agent-ready ticket with acceptance criteria, scope, and non-goals. Then identify at least two sub-tasks a Design stage would create from it, and which one blocks the other.

Tell Chiron your rewritten ticket and sub-task breakdown before moving to Unit B3, where we cover how those sub-tasks turn into actual branches and PRs.
