Start with a dance, not an orchestra

An orchestra has a conductor: one person, one baton, every musician watching for the cue. If the conductor stops, the music stops.

A folk dance has no conductor. Dancers watch each other and the music itself, and know their move because of what just happened, not because someone directed them. Remove any one dancer and the dance continues - the others adapt to the state of the floor.

The principle

Orchestration means a central controller decides and directs every step. Choreography means independent agents watch shared state and react - no central controller required. This pipeline is choreography: there is no master process telling the Requirements agent, then the Design agent, then the Build agent, what to do in sequence. Each agent watches ticket labels and acts when it sees work addressed to its stage.
Orchestration
One controller calls every step. Fragile if the controller fails. Simple to reason about centrally.
Choreography (this pipeline)
Agents react to shared state independently. Resilient - no single point of failure. Harder to see "the whole picture" at a glance - you have to read the state.

The mechanism: labels as the entire coordination layer

A ticket's label is not a cosmetic tag. It is the coordination protocol:

stage:<name>-ready -> an agent should pick this up now stage:<name>-running -> an agent is actively working it stage:<name>-done -> this stage finished; next stage's agent should now see a -ready label appear stage:<name>-await -> stopped for a human decision; no agent will proceed until a human acts stage:blocked -> something is wrong; nothing proceeds until a human investigates

The poller watching all this is deliberately "dumb" - it does not second-guess an agent's output. If an agent says a stage is done, the poller advances the label. It does not evaluate quality. That evaluation is the agent's (or your) job, before declaring done.

Try it yourself

Open sandbox.html and use Panel 1 (the mock ticket board). Try clicking "Skip to Build" while the ticket is still at stage:requirements-ready.

Watch what the event log says. That rejection is exactly what a real choreography poller would do: it will not advance a ticket through an invalid transition, no matter how badly you want to skip ahead. The valid path has to be walked in order.

Worked example

A ticket sits at stage:design-done. The Build agent is watching for stage:build-ready. Nobody manually tells the Build agent "your turn" - the moment something (a human or the Design agent) applies the stage:build-ready label, the Build agent notices and starts, because that is the state it watches for.

If you, as the FDE, want the Build agent to look at something right now, you don't message it - you make sure the ticket's label is correctly at stage:build-ready. That is the "orchestration" move inside this specific mechanism (tying back to Track A's Unit A2: the smallest useful action is often "get the system state right," not "do the work yourself").

Self-check

In the sandbox, try two more invalid transitions and one valid chain all the way to stage:build-ready. What's the shortest valid path from stage:requirements-ready to stage:build-ready, and what would happen if a label got stuck at stage:design-await with nobody watching?
