Unit B4 - Deploy / Change Management

FDE Dojo / Track B / Unit B4

Start with a merge that isn't done

The PR from Unit B3 merges. Tests passed. The code is in the main branch. An engineer trained only on output would call this "done."

It isn't. Nothing has shipped to anyone yet, nobody has verified the change behaves correctly in a real environment, and - critically, tying straight back to Track A's Unit A4 - nobody has checked whether the business outcome actually moved. Merging is a milestone inside Build, not the end of the pipeline.

The principle

"Done" in an agentic pipeline is a label, not a merge. The ticket only reaches a genuinely final state when deployment is verified and the evidence trail - what changed, why, and what effect it had - is recorded where the next person (or agent) can see it. A merged PR with no corresponding ticket-state update is invisible to the rest of the choreography: no agent or human downstream knows the work actually happened.

The FDE's job at cutover

Three things an FDE owns at this stage that no agent owns for you:

  • Verification in the real environment - did the deployed change actually behave as expected, not just as tested in isolation?
  • Rollback awareness - if this breaks something, what's the fastest safe path back, and do you know it before you need it, not after?
  • Communication - telling the stakeholder (the same one from Track A's Unit A1 who had the ambiguous ask) that it shipped, and starting the outcome-check clock from Unit A4.

Worked example

The handoff-delay instrumentation from Units B2/B3 deploys. The FDE's cutover checklist:

  1. Confirm the instrumentation is actually producing data in production, not just passing tests against sample data.
  2. Know that if the instrumentation misbehaves, the rollback is reverting one config flag, not a code rollback - confirmed before deploying, not discovered during an incident.
  3. Message the stakeholder: "Instrumentation is live. I'll have delay-source data in a week, and we'll know if the 48-hour target is realistic by then" - directly setting up the Unit A4 outcome-check sentence.
This is also where the ticket's label finally reaches a true end state - not stage:build-done, but something like stage:released or stage:verified - with the evidence (what was checked, what the result was) in the ticket's comments, visible to anyone who looks later.

Self-check

Think of the last thing you (or someone you know) called "done" right after a merge. Walk through the three cutover items above for it, honestly. How many were actually done at that point?
