Start with a PR nobody can trace

A branch called my-fix. A PR titled "quick fix." Somewhere in the description, maybe, a mention of a ticket number - or maybe not.

A human reviewer might eventually figure out what this relates to by asking around. An automated system - the one that links GitHub activity back to a ticket's label state - cannot. If the branch and PR don't follow the convention, the choreography from Unit B1 breaks: the ticket never advances, because nothing told it the work happened.

The principle

Naming conventions are not style preference here - they are the mechanism that lets GitHub activity update ticket state automatically. Get the convention right and the system does the tracking for you. Get it wrong and you've silently broken the traceability this entire pipeline depends on.

The convention

branch: <type>/<TICKET-KEY>-<kebab-summary> e.g. feature/SANDBOX-101-add-renewal-reminder PR title: should reference the ticket key somewhere, e.g. "Add renewal reminder email (Refs SANDBOX-101)" <type> is one of: feature, fix, chore, docs

This is exactly what Panel 2 of sandbox.html validates. The pattern isn't arbitrary - it is what the GitHub-to-ticket integration matches on to auto-link activity to the correct ticket.

Try it yourself

Open sandbox.html and try a few branch names in Panel 2 - some that follow the convention, some that don't (missing the type prefix, wrong ticket key, no kebab-case). Then try a few PR titles, some referencing the ticket key and some not.

Notice the pattern in what passes vs. fails - that pattern is the actual mechanism a real integration uses, not a Dojo-only rule.

Dividing the work: human FDE vs. build/test agents

The human FDE verifies
Does this solve the actual business problem (tie back to Track A)? Is the scope right? Would a domain expert agree this is correct?
Build/Test agents verify
Does the code compile, pass tests, meet style/security conformance? Mechanical correctness - the things a pattern-matcher is good at.

An FDE who tries to do the agent's job (manually checking every test pass) is wasting the orchestration the pipeline already provides. An FDE who skips their own job (does this solve the actual problem) and just waits for green checkmarks has shipped output, not outcome - directly the Unit A4 failure mode, now showing up as "I trusted the pipeline instead of checking the business result."

Worked example

Sub-task from Unit B2: "instrument the handoff step to measure current delay sources." Branch: feature/SANDBOX-101-instrument-handoff-delay. PR title: "Add handoff delay instrumentation (Refs SANDBOX-101)." Test agent runs automatically on the PR and reports pass/fail on code correctness. The FDE's separate job: once merged and deployed, actually look at the instrumentation data (tie-back to Unit A4's outcome check) - the Test agent will never tell you whether the delay source you found is the real bottleneck, only whether your code runs correctly.
